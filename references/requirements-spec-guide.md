# 需求文档规范

## 文件位置

- 当前：`docs/dev/sdd/requirements.md`
- 归档：`docs/archive/YYYYMMDD-<主题名>/sdd/requirements.md`

## 文档结构

```markdown
# 需求规格说明书 — {标题}
> 分支 / 最后更新

## 目标
[2-3 句话核心目标，后续设计和实现围绕此目标校准]

## 背景
[简述项目和当前阶段]

## 已完成的用户故事
### US-001: {标题}（✅ Phase N）
[保留验收标准供参考]

## 当前用户故事
### US-NNN: {标题}
[详细描述]

## 约束与禁止事项
[明确不允许做的事情，防止范围漂移]
```

## 用户故事模板

```markdown
### US-{NNN}: {标题}
- **角色**：作为 {用户角色}
- **需求**：我希望 {具体需求}
- **目的**：以便于 {业务目标}
- **优先级**：P0/P1/P2
- **验收标准**：
  1. {可测量条件}
  2. {可测量条件}
```

## 编写要点

**US 编号**：同一 requirements.md 内全局递增。新 Phase 追加时继续已有编号，不重新从 001 开始。

**优先级**：
- P0 = 阻塞性，立即处理
- P1 = 核心功能，本迭代完成
- P2 = 可选，排期处理

**验收标准**：必须可测量。

| 好 | 差 |
|---|---|
| 点击后 2 秒内完成加载 | 加载要快 |
| 密码错误 3 次锁定 15 分钟 | 密码错误后要锁定 |
| 触发保存后 2 秒内显示成功状态 | 保存体验要顺畅 |

**约束与禁止事项**：列出代理/开发者不应做的事。来源于用户明确指示、设计决策或系统边界。防止自行扩展范围。

**Research 边界**：`docs/dev/research/{主题}.md` 可记录讨论和探索，但不能替代需求事实。若调研内容影响目标、范围、验收标准，必须回写到 `requirements.md`。

**流程**：requirements.md → design.md → requirements-design-review → 用户确认 → 任务拆解。禁止跳过需求或 AI Review Gate 直接进入实现。
