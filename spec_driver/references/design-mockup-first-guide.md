# Design Mockup First 设计先行技能

## 核心理念

**先单 HTML 确认，再写代码。** 设计新 UI 或功能时，直接写 React/组件代码容易因理解偏差导致返工。用单 HTML 低保真原型先和用户对齐，确认后再实现，更省时。

所有 UI 需求都必须以项目存量样式风格为基础进行设计，禁止自由发挥新的 UI 样式风格。先读取需求关联的现有页面、组件或相邻功能，还原其布局、密度、色彩、字号、间距、交互状态和组件形态；还原完成后，再在同一风格体系上叠加新功能。

新功能 mockup 要尽量满足需求中的交互要求，优先保证功能交互完整性，而不是只产出静态 UI 稿。低保真原型也应覆盖主要操作路径、状态变化和用户决策点，让用户能确认功能流程是否成立。

---

## 何时使用

| 场景 | 建议 |
|------|------|
| 设计新面板、新页面布局 | ✅ 先单 HTML mockup |
| 设计新组件交互流程 | ✅ 先单 HTML mockup |
| 设计多区块组合的整体效果 | ✅ 先单 HTML mockup |
| 与用户/PM 确认设计是否一致 | ✅ 单 HTML 最直观 |
| 小改现有组件样式 | 可直接改代码 |

**触发词**：设计、布局、UI 原型、mockup、低保真、整体效果、确认设计

---

## 推荐流程

```
1. 讨论需求与信息架构
   ↓
2. 读取需求关联的存量页面/组件，确认现有样式基准
   ↓
3. 先用单 HTML 还原现有页面风格与基础布局
   ↓
4. 在还原稿上叠加新功能，生成单 HTML 低保真原型（内联 CSS/JS）
   ↓
5. 用户在浏览器打开确认：是否和预期一致？
   ↓
6. 根据反馈迭代 mockup（不改代码，只改 HTML）
   ↓
7. 确认后再开始写 React/真实代码
```

---

## 单 HTML 原型要点

### 产出物

- **路径**：`docs/dev/ui/{功能名}_v1.html`（迭代时可增加 `_v2.html` 等）
- **格式**：单文件，内联 CSS + 内联 JS（可选）
- **目的**：快速预览、确认布局与信息架构，无需启动项目

**示例**：`docs/dev/ui/work-session_v1.html`、`docs/dev/ui/settings-panel_v1.html`

### 内容建议

1. **整体布局**：与目标应用保持一致（侧边栏、头部、主内容区）
2. **信息架构**：展示主要区块、层级、标签
3. **关键交互**：按钮、Tab、列表项等占位，可加简单 hover
4. **设计规范**：遵循项目设计 tokens（如 Otia 的 otia-component-style）
5. **存量风格还原**：先复刻需求相关页面的布局密度、色彩、字号、间距、边框、阴影、圆角、按钮和表单样式，再叠加新功能
6. **实现可还原性**：后续开发应能只拿 mock 稿就还原功能；mock 中必须体现关键状态、空态、加载态、错误态、禁用态等必要交互规则
7. **交互完成性**：尽量覆盖从入口、操作、反馈、确认到完成的闭环，不能只展示最终静态界面

### Mock 代码要求

- 在 HTML 注释或就近结构中写明关键规则，例如数据状态、按钮可用条件、列表排序、筛选逻辑、确认弹窗、错误提示和继续执行条件。
- CSS 命名和结构要贴近真实组件边界，方便后续映射到 React/真实代码。
- 对新增功能区块标注与存量页面的关系：复用哪个区域、替换哪个区域、插入哪个位置、是否影响原有交互。
- 不只画静态视觉，要让后续 AI 能理解用户需求、状态变化和交互意图。
- 能用少量内联 JS 表达的交互，应优先做成可点击/可切换/可展开的原型，帮助用户确认流程。

### 避免

- 不要写完整业务逻辑
- 不要接入真实 API
- 不要过度美化（低保真即可）
- 不要脱离项目现有风格自由设计新的视觉体系
- 不要只画新增功能而忽略它嵌入存量页面后的整体效果
- 不要把新功能 mockup 做成只有视觉摆放、没有关键操作路径的静态稿

## 案例：工作会话 UI 设计

### 背景

设计「执行开发」阶段的工作会话 UI，需要确认：阶段 + 一进程一卡片 + Chat 快速下发的整体效果。

### 流程

1. **需求澄清**：一进程一对话、不暴露 agent 概念、要有 Chat 下发 + @mention + 是否继续执行
2. **初版 mockup**：单 HTML，只有阶段 + 工作会话卡片
3. **用户反馈**：结合开发助手整体、要有 Chat、要明确谁在干活
4. **迭代 mockup**：加上 Chat Room、成员栏、@mention、是否继续确认、优化卡片布局
5. **确认后**：再落地到 React 组件

### 产出

`docs/dev/ui/work-session_v1.html` — 单 HTML 展示完整执行开发界面，用户打开即可确认。

## 检查清单

开始写真实代码前，确认：

- [ ] 已读取需求相关的存量页面/组件
- [ ] mockup 已先还原项目现有 UI 风格，再叠加新功能
- [ ] 已有单 HTML 低保真原型
- [ ] 用户在浏览器打开并确认布局/信息架构
- [ ] 关键区块（如 Chat、工作会话卡片）已明确
- [ ] 设计规范已参考（如 otia-component-style）
- [ ] mock 代码中已写明关键交互规则，后续开发可据此还原功能
- [ ] 新功能主要交互路径已在 mockup 中体现，可用于确认功能闭环

---

## 一句话总结

> 设计新 UI 时，**先单 HTML mockup 确认**，避免代码写开后再返工浪费时间。
