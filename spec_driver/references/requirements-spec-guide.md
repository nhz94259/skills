# 需求文档规范

## 文件位置

- 当前：`docs/dev/sdd/requirements.md`
- 归档：`docs/archive/YYYYMMDD-<主题名>/sdd/requirements.md`

## 通用可读性要求

需求文档是给用户、开发者、review agent 和后续接手者共同阅读的事实源，必须结构清晰、可快速定位：

- 开头先给目标和背景，不先铺细节。
- 范围、用户故事、验收标准、测试用例优先用表格或稳定小节表达。
- 每个 US 只讲一个用户价值，不把多个不相关诉求塞进同一条。
- 长清单超过 8 条时拆成表格或分组小节。
- 引用块只用于重要提示、边界和风险，不用大段加粗替代结构。
- 不内嵌大段 HTML；如果用户要求额外 HTML 阅读版，也必须以 `requirements.md` 为事实源同步生成。

## 推荐阅读结构

需求文档应接近“评审页”的阅读体验，而不是普通笔记。推荐结构：

| 阅读区块 | Markdown 表达 | 目的 |
|----------|---------------|------|
| 首屏摘要 | 标题 + 文档信息表 + 2-3 句话摘要 | 让读者先知道主题、状态、范围 |
| 目标 | 2-3 句话 | 校准后续设计和任务边界 |
| 背景 | 短段落 + `> 注意：...` | 说明为什么要做和容易误解的点 |
| 范围 | `In Scope / Out of Scope` 双列表表格 | 像卡片一样快速对比做/不做 |
| 用户故事 | US 矩阵表 + 必要时补详情小节 | 快速扫描用户价值和验收标准 |
| 测试用例 | TC 矩阵表 | 快速看覆盖面和预期 |
| 约束与风险 | 表格或短 bullet | 暴露不可做事项和剩余风险 |

## 用户故事模板

```markdown
### US-{NNN}: {标题}
| 字段 | 内容 |
|------|------|
| 角色 | 作为 {用户角色} |
| 需求 | 我希望 {具体需求} |
| 目的 | 以便于 {业务目标} |
| 优先级 | P0/P1/P2 |
| 验收标准 | 1. {可测量条件}<br>2. {可测量条件} |
```

## 编写要点

**US 编号**：同一 requirements.md 内全局递增。新 Phase 追加时继续已有编号，不重新从 001 开始。

**优先级**：
- P0 = 阻塞性，立即处理
- P1 = 核心功能，本迭代完成
- P2 = 可选，排期处理

**验收标准**：必须可测量。

| 好 | 差 |
|---|---|
| 点击后 2 秒内完成加载 | 加载要快 |
| 密码错误 3 次锁定 15 分钟 | 密码错误后要锁定 |
| 触发保存后 2 秒内显示成功状态 | 保存体验要顺畅 |

**约束与禁止事项**：列出代理/开发者不应做的事。来源于用户明确指示、设计决策或系统边界。防止自行扩展范围。

**测试用例可读性**：TC 必须让非作者能理解“输入/动作/预期”，不要只写内部函数名。复杂 TC 用表格承载，必要时再补短段解释。

**Research 边界**：`docs/dev/research/{主题}.md` 可记录讨论和探索，但不能替代需求事实。若调研内容影响目标、范围、验收标准，必须回写到 `requirements.md`。

**流程**：requirements.md → design.md → requirements-design-review → 用户确认 → 任务拆解。禁止跳过需求或 AI Review Gate 直接进入实现。
