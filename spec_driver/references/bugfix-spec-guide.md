# Bugfix 规范

Phase 验收后发现遗留问题时使用。核心：**先全面盘点、再分批修复、按优先级推进**。

本文件定义的是 `docs/dev/sdd/` 下 Bugfix 的**过程规范**，并约束何时把有价值修复经验沉淀到 `docs/bugfix/`：
- `bugfix-plan{N}.md` / `bugfix-task{N}.md` 用来管理盘点、拆分、执行和验证
- 若修复结果需要沉淀为长期可检索的问题记录，再补 `docs/bugfix/_INDEX.md` 和 `docs/bugfix/bug-{YYYYMMDD}-{序号}-{描述}.md`

## 触发时机

| 场景 | 说明 |
|------|------|
| Phase 验收发现缺口 | 任务标 ✅ 但功能未闭环（placeholder、未接线、事件未订阅） |
| 代码级复查 | 对比设计文档与代码实现，发现偏差 |
| 手动验证失败 | 按验证步骤执行，某些步骤无法通过 |
| 类型约束问题 | `any` / 宽泛对象逃逸、联合类型不完整、缺少运行时校验 |
| 集成断裂 | IPC 未打通、UI 回调未接线 |

## 文件命名

```
docs/dev/sdd/
├── bugfix-plan{N}.md       ← Gap 盘点（1 个 plan 可拆多个 task）
├── bugfix-task{N}.md       ← 修复任务
```

编号从 1 递增，不跳号。

## 两阶段工作流

### 阶段 1：Gap 盘点 → bugfix-plan{N}.md

**盘点方法**：
1. 逐条检查 task-execution-plan.md 的验证步骤
2. 对比设计文档与代码实现（找 placeholder / TODO / 未接线 / 类型或边界逃逸）
3. 跑仓库的静态检查和相关测试

**文档结构**：
```markdown
# Plan {N} — {标题}
> 日期 / 来源 / 前提

## Gap 总览
| # | 问题 | 优先级 | 类别 | Phase |

## 🔴 P0：阻塞用户使用
### G1：{标题}
**现状**：{代码片段+行号}
**影响**：{什么功能不可用}
**修复方案**：{简要思路}
**涉及文件**：{路径列表}

## 🟡 P1：功能不完整
## 🟢 P2：后续迭代
## 建议的执行顺序
## 最小可用集
```

### 阶段 2：修复任务 → bugfix-task{N}.md

**拆分原则**：P0 先修 → P1 次之 → P2 最后；相关 Gap 合并；每 task ≤ 9 个文件。
**单目标更新**：一次状态变更只允许完成一个 `G{N}` 或一个 `bugfix-task{N}` 的目标范围，禁止在验证单个问题时顺手把其他 Gap 一起标 ✅。

**并发边界**：
- P0 默认优先串行，先恢复核心可用性；P0 未恢复前，不调度依赖该能力的 P1/P2 并发修复。
- P1/P2 只有在写入范围不重叠、依赖不冲突、验证方式独立时才允许并发。
- 同一公共模块、同一接口、同一状态文件、同一验证脚本或同一 Gap 状态更新必须串行。
- 每个 Gap 必须独立验证；禁止用一个 Gap 的验证结果顺手标记其他 Gap。
- 任两个 Gap 写入范围交叉时，相关修复回退串行，并指定单一 owner。

**文档结构**：
```markdown
# bugfix-task{N}：{标题}
## Context

## G{X}：{Gap 标题}
### 问题 / ### 方案 / ### 涉及文件

## 改动文件汇总
| # | 文件 | 操作 | Gap |

## 验证
{仓库静态检查命令}
{仓库测试命令}
手动验证步骤
```

## Gap 优先级

| 优先级 | 标记 | 含义 | 处理时机 |
|--------|------|------|----------|
| P0 | 🔴 | 核心功能无法工作 | 立即修复 |
| P1 | 🟡 | 功能不完整、影响体验 | 当前批次 |
| P2 | 🟢 | 优化项 | 下一批次或按需 |
| 验证 | ⚪ | 需手动确认 | 随时可做 |

## Gap 类别

| 类别 | 典型表现 |
|------|----------|
| UI 接线 | props 声明了但调用方未传入 |
| 后端 | placeholder 函数、`async () => []` |
| 前后端打通 | 事件未订阅、channel 未注册 |
| 类型约束 | `any`、宽泛对象逃逸、联合类型不完整 |
| 前端状态 | state 缺少业务字段 |
| 数据打通 | 两套独立数据互不关联 |

## 验证标准

bugfix-task 标记完成前：
- ✅ 相关静态检查通过
- ✅ 相关测试全部 PASS
- ✅ 手动验证步骤执行通过
- ✅ 并发修复已完成必要集成验证；单 Gap 串行修复可写 N/A
- ✅ bugfix-plan 中对应 Gap 状态更新为 ✅

## 结果沉淀（缺陷记录）

以下情况建议在完成 `bugfix-task` 后，再补一份 `docs/bugfix/bug-{YYYYMMDD}-{序号}-{描述}.md`：

- 用户明确反馈过、未来可能再次出现
- 根因复杂，值得保留排查路径
- 需要跨会话、跨成员复用修复经验
- 该问题已脱离当前 Phase，成为独立缺陷知识

记录要求：

- 维护 `docs/bugfix/_INDEX.md`，至少包含 Bug ID、标题、严重程度、状态、修复时间
- 单条 Bug 记录至少包含：问题信息、问题现象、复现步骤、期望行为、实际行为、根本原因、影响评估、修复内容、验证结果
- Bug ID 采用 `bug-{YYYYMMDD}-{序号}`，文件名采用 `bug-{YYYYMMDD}-{序号}-{描述}.md`

边界：

- `docs/dev/sdd/bugfix-plan*.md` / `bugfix-task*.md`：过程文档
- `docs/bugfix/bug-*.md`：结果文档 / 有价值修复经验沉淀

## 禁止行为

- ❌ 不做 Gap 盘点直接改代码
- ❌ 把所有 Gap 堆在一个 bugfix-task
- ❌ 修 P1 之前不修 P0
- ❌ P0 未恢复前并发修依赖该能力的 P1/P2
- ❌ 共享模块、接口、状态文件或验证脚本冲突时强行并发
- ❌ 验证一个 Gap 时顺手把其他 Gap 一起标 ✅
- ❌ 修复后不跑相关检查和测试
- ❌ 跳过手动验证直接标记完成
